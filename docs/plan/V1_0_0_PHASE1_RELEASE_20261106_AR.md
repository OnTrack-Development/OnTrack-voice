# OnTrack Voice v1.0.0 — العقد التنفيذي للمرحلة الأولى
**تاريخ الاعتماد للمواصفات:** 2026-11-06. **الحالة الحالية:** تنفيذ جزئي. آخر نشر SaaS فقط مؤكد: Commit `32056460acd1`، Run `42173660235` ناجح وإيصالات Host QA/Deploy ناجحة؛ لا يوجد اعتماد Stable 1.0.0 كاملة أو Device E2E.
**الموقع:** app.ontrackegy.com؛ **الجهاز المرجعي:** Xiaomi Note 12 Pro 5G.
**مصدر الحقيقة:** آخر قرارات المالك في جلسة نوفمبر 2026 تتقدم على خارطة نوفمبر 3 فيما يتعلق بنطاق المرحلة الأولى.

## 1) خط الأساس والدليل
- صاحب المشروع يؤكد أن **ربط حساب الأدمن الحالي يعمل** من التجربة الأولى ولم يُفك؛ لا تعاد التهيئة ولا يُحذف pairing/token/data بلا داع.
- صاحب المشروع يؤكد **أن الرد التلقائي والكتم يعملان جيدًا**. الصوت مستقر وجيد على Wi-Fi، وعلى 4G يوجد تكدس/تأخير وميل للإطالة؛ لا تعلن أن الاثنين معطلان اعتمادًا على تقرير تاريخي.
- Gemini Live يعمل صوتيًا لكن تحسين turn-taking وتقليل الإطالة ومنع هلوسة التفريغ لم يُغلق باختبار قبول.
- يوجد محرر Flow رسومي، لكنه غير كافٍ في التنفيذ الذكي؛ السيناريو النصي المفصل يعطي نتائج أفضل حاليًا.
- Knowledge Base المطلوبة (مجلدات + PDF/DOCX/TXT/MD + معالجة وتعارضات ومزامنة/API caching) **غير مكتملة**؛ وجود مخزن chunks سابق لا يحقق مواصفات المستخدم.
- تكامل العمليات الحقيقية (WHMCS/Laravel/حجوزات) **غير منفذ End-to-End**؛ أدوات وWebhooks عامة لا تعني أن الحجز أو التذكرة يعملان عبر مكالمة.
- سجلات مكالمات أولية موجودة، لكن **ملخصات سياقية ونتائج إجراءات منظمة غير مكتملة**.
- لا يثبت أي إصدار منشور قبل تطابق SHA، CI، host receipt، وتجربة SIM فعلية.

## 2) ما يجب تسليمه في إصدار واحد v1.0.0
### A — الجهاز والمكالمات
- الإبقاء على SIM وصوتها كما هما دون تغيير المسار العامل بغير اختبار رجعي.
- الموبايل = جسر تحكم/صوت. الأزرار الدائمة: تشغيل/إيقاف، حالة الشريحة والإيجنت وتعيين المصدر، صلاحيات التشغيل، تحديث التطبيق، فتح لوحة الويب **في المتصفح الخارجي**.
- معالج أول تشغيل فقط عند عدم اكتمال الجاهزية؛ ربط الحساب، الأذونات الأساسية، خيارات إعداد الجهاز الضرورية (Wireless/USB debugging حسب آلية الجهاز)، اختبار readiness. عند نجاح الإعداد لا يعيد إزعاج المستخدم؛ يظهر «إصلاح التفعيل» فقط عند مشكلة فعلية.
- التفعيل المتكرر عند كل دخول غير مقبول؛ حفظ الربط الحالي والتعامل مع فقد اتصال Debugging عند تغير الشبكة أو إعادة تشغيل الجهاز دون ادعاء أنه دائم.
- إثبات الرد التلقائي، mute وunmute، وصول PCM ثنائي الاتجاه، المقاطعات، إنهاء مكالمة الشريحة الفعلي، التعافي من التغيير بين Wi-Fi و4G، من غير Accessibility.
- معالجة تكدس 4G: bounded jitter buffer، drop stale audio، قياس transport/RTT/VAD/queue latency، إعادة تزامن منضبطة، عدم الانتظار حتى ينتهي الصوت القديم. عدم فقد سياق المكالمة.
- تقليل ثرثرة الإيجنت، الاستماع حتى انتهاء دور العميل، مصرية طبيعية، عدم الاعتراف بأنه سيناريو، لا حقائق مختلقة.

### B — العقل ومصادر المعرفة
- Knowledge Base مستقلة لكل Tenant/Site/Agent بفولدرات وملفات PDF/DOCX/TXT/MD/روابط مع versioning، validation، dedupe، conflicting-source review، crawl provenance، index status، update scheduling/trigger.
- مصدران رسميان للمعلومة: ملفات/محتوى محلي موثق، وواجهات API حيّة. تُخزّن البيانات شبه الثابتة مع TTL/source priority؛ معلومات الحجوزات والفواتير والحالات الحرجة تُراجع حيًا قبل تنفيذ أو تأكيد.
- لا يُقال «تم» لأي طلب إلا بعد تلقي نجاح API مع معرف العملية الحقيقي، وتسجيل idempotency/audit.
- Flow Builder: Intent/Reasoning/Knowledge/Tool/Validation/Approval/Fallback nodes، Draft/Test/Publish/Rollback، إصلاح Invalid node type، محاكاة واختبارات وtrace لكل انتقال؛ السيناريو النصي المفصل يظل مسارًا صالحًا مستقلًا.

### C — التكاملات
- Integration Manager يدعم Generic REST/OpenAPI/Laravel/WHMCS، أسرار مشفرة بالهوست، scope/allowlists، تجارب اتصال، صلاحيات قراءة/كتابة وسياسات موافقة، منع SSRF والتصرف من model وحده.
- حجز العيادة: المواعيد المتاحة -> بيانات الاسم والهاتف -> قراءة تأكيد -> حجز API -> معرف الحجز وتوقيت الحضور من النظام. فشل الطلب لا ينتج تأكيدًا.
- WHMCS: تعرف هوية مع تحقق إضافي قبل بيانات حساسة؛ جلب خدمات/فواتير/أسعار وخطط؛ صياغة تذكرة وقراءتها للعميل؛ إنشاء بعد موافقة صريحة فقط؛ إضافة رد/متابعة. **ممنوع تعليق/حذف/إغلاق خدمة أو تذكرة تلقائيًا**.
- Laravel: discovery/schema mapping، الاستعلام والطلب والحجز بحسب العمليات المسموحة، مع تأكيد وتدقيق وتزامن الحالة.

### D — نتائج المكالمة
- Transcript مرتب ومتواصل نسبيًا، timing وspeaker labels لا fragment spam؛ تنقية الأخطاء من السياق دون اختلاق أسماء/أرقام.
- Summary سياقي موجز، intent/outcome، البيانات المجمعة، اسم العميل إن وثق، booking/ticket/invoice IDs، نجاح/رفض/تعذر، follow-up، طلب موظف دون تنفيذه تلقائيًا.
- Tool traces مستقلة عن ملخص العميل، أرقام حقيقية، event correlation، خصوصية وسجلات قابلة للمراجعة.

### E — أسرار المحرك ونسخة APK
- **قرار ملزم:** APK الأساسي لا يتضمن تنفيذ capture/injection/audio routing الحساس متى أمكن فصله تقنيًا. المحرك منفصل على السيرفر مع تحميل وحدات موقعة ومشفرة فقط بعد مصادقة وترخيص، والتحقق من checksum/signature والاستحقاق؛ تجنب وضع المصدر/البرومبت/المفاتيح في الحزمة.
- بروتوكول المحرك المحلي ومسار PCM وما يفرضه Android قد يبقيان قابلين للرصد؛ مجرد التحميل عند التفعيل لا يجعل نسخة المحرك الموجودة على جهاز العميل غير قابلة للاستخراج. شرط القبول: محاولة استخراج من **APK الأساسي وحده** لا تعطي الكود المنفصل، مع اختبارات تحليل ديناميكي مستقلة للمخاطر المتبقية.
- استخدم تشويش R8/Native عند ملاءمته، لا تسرب سجلات أو تعليقات/مراجع تحليل في الأصول الموزعة. لا تمس إشعارات تراخيص المصدر المفتوح الواجبة. لا تُحدث تلفًا متعمدًا لملفات جهاز العميل.
- توزيع APK ديناميكي من خارج Play خاضع لاختبارات توافق ومراجعة أمنية؛ يجب تحديد القنوات المدعومة قانونيًا وتقنيًا.
- لا تعطل محرك الصوت الحالي قبل بناء مسار بديل قابل للتحقق على نفس الهاتف.

### F — SaaS ولوحة التحكم
- التسجيل User/Reseller وخطوات الدخول واستعادة كلمة السر تعمل مع عزل tenants.
- إعداد Platform «إظهار الريسيلرز» (افتراضي enabled للمحافظة على الوضع): عند التعطيل تُخفى إدخالات الريسيلرز وروابط تسجيلهم وخططهم حتى من لوحة الأدمن. لا تمس الحسابات والاشتراكات القائمة ولا تفك أي ربط. يجب حماية POST والتحقق النهائي من التسجيل.
- واجهة العميل: Agents/Scenario/Flow/Knowledge/API/Calls/Devices/Settings بشكل واضح؛ تجنب إظهار الحملات والجدولة وإضافات الأصوات ومكالمات المدير والتحكم التقني المتكرر في نسخة v1.
- الادمن: الإعدادات الضرورية للحسابات والباقة والأمان والربط والتكاملات؛ عناصر Phase 2 تُحجب عن التنقل مع بقاء نسخة أرشيفية.

## 6) تكملة الاتفاقات الملزمة التي لم تكن مكتوبة في النسخة الأولى
**نوع الإضافة: متطلبات ومعايير قبول فقط؛ لا يُفهم من تدوينها أنها منفذة أو مُختبرة أو منشورة.** هذه القرارات الأحدث في جلسة 6 نوفمبر 2026 تُكمّل الفصول 1–5 وتسبق أي تعارض في خطط 1–3 نوفمبر. لا توسعة اجتهادية للمرحلة الأولى؛ المرحلة الثانية محفوظة بلا حذف.

### 6.1) قرار المصادقة المؤقت وأمان الحسابات
- **في التطوير والتجارب الداخلية: إيقاف المصادقة الثنائية 2FA وOTP وTOTP وAuthenticator لجميع الأدوار بدون استثناء: Platform Admin وAdmin وReseller وUser.** تسجيل الدخول يكون بالبريد وكلمة المرور فقط، دون شاشة رمز أو إجبار المستخدم على ربط Authenticator. يشمل القرار الأدمن المالك.
- يُعاد تفعيل 2FA **عند الانتقال للإطلاق التجاري الفعلي فقط** بقرار من المالك واختبارات تسجيل/استرداد مناسبة. أي شرط قديم يقول بفرض 2FA حاليًا يعتبر متجاوزًا خلال التجارب. يظل تحقق الهوية والموافقة قبل كشف معلومات WHMCS الحساسة أو تنفيذ عملية مالية مستقلًا وملزمًا.
- يظل RBAC، عزل tenants، CSRF، التحقق الخادمي من POST والـAPI، تشفير كلمات المرور والأسرار، سياسات الجلسات، password reset/change، والـAudit إلزاميًا. تعطيل OTP مؤقتًا لا يبرر تعطيل وسائل الأمان الأخرى.
- المالك الإداري في التجارب لا تُغلق وظائفه بسبب حدود باقة مستخدمين. الحساب النشط غير الموقوف لا يُعامل وكأن اشتراكه يُجدد أو ينتهي يوميًا، ولا تُلغى بيانات الحساب أو ربطه عند تحديث النسخة.
- Android يعتمد على جلسة حساب الـSaaS وربط الجهاز الحالي ولا يطلب مفتاح API جديدًا من المالك في كل دخول. لا إعادة إقران هاتف أو SIM أو مسح token/data بلا سبب مثبت.

### 6.2) إدارة مفاتيح الصوت ومفاتيح مساعد Flow
- Google Gemini Live مزود الصوت الأساسي، مع قابلية إضافة Google وOmnira A/B وNVIDIA وCustom HTTPS للمهمة التي تدعمها واجهة كل مزود بالفعل. عدم الخلط بين TTS عادي وRealtime bidirectional؛ اختيار المزود يعتمد على اختبار البروتوكول الفعلي لا اسم الموديل.
- مجموعتان مستقلتان في Platform Admin: **Voice Live keys** و**Assistant/Flow text keys**؛ لا استخدام تلقائي لمفتاح Voice في Assistant أو العكس. تدعم كل مجموعة 3–4 مفاتيح أو أكثر للمسؤول دون حد اصطناعي، وأولوية مفاتيح/مزودين، وإضافة مفاتيح خاصة بالريسيلر أو المستخدم وفق حدود الباقة وصلاحيات tenant.
- عند Rate-limit/429/Quota أو اختناق موثق: يتوقف اختيار المفتاح المتأثر **15 دقيقة = 900 ثانية**، ثم تُجرَّب عودته بضوابط. يُبدَّل إلى مفتاح آخر متاح آليًا بلا دوامة retries غير محدودة، مع تتبع سبب التبديل والكمون/الأخطاء 403 و429 و5xx دون كشف المفاتيح.
- أثناء المكالمة يجب **حفظ سياق الحوار وحالة العقدة والدور** عند تبديل المفتاح/المزود. نافذة hold/recovery المطلوبة للمفتاح المتأثر عند الضرورة 30–120 ثانية هي سياسة تعافٍ، **وليست زمن تأخير مقبولًا للعميل أو إثبات نجاح**؛ تُختبر استمرارية الصوت عمليًا.
- تخزن المفاتيح والأسرار server-side مشفرة، ولا تُشحن مع APK أو واجهة HTML/JS أو GitHub logs. اختبار صلاحية الموديل يجب أن يولد استجابة حقيقية وليس مجرد HTTP 200.

### 6.3) جودة الصوت و4G والـTurn-taking
- شخصية الإيجنت: ودودة، مرحة، مصرية طبيعية، وغير رسمية بشكل مناسب؛ لا تباطؤ أو رسمية مصطنعة ولا جمل طويلة بلا داع. تسمع العميل للنهاية قبل الرد، تقبل مقاطعته، لا تعيد الترحيب كل مرة، وتعود لنفس نقطة Flow بعد سؤال جانبي. سيناريوهات الاختبار الهزلية لا تُقدَّم كحقائق أو عمليات بيع/حجز حقيقية.
- التمييز بين صوت العميل، وتفريغ ما سُمع، ونص رد الإيجنت، والصوت الذي نُطق فعليًا. أي هلوسة في transcription تُشخّص بمقارنة صوت/نص وtimestamps/ASR قبل إنشاء اسم أو رقم أو معلومة مزيفة. عند عدم اليقين يُسأل العميل للتأكيد.
- يُقاس first-audio وend-of-turn وVAD وRTT وqueue depth وPCM/drop وp50/p95 لكل من Wi-Fi و4G؛ وصول أول استجابة خلال 500–900ms مع انقطاع بعدها **ليس نجاحًا**، وزمن 12400ms في مزود/بوابة صوت لا يُعد Realtime. تُمنع الجمل المقطوعة وصوت متراكم قديم على بيانات الهاتف.
- رد SIM التلقائي بعد **5 ثوانٍ** وفق Phone Control Center، دون أن يتكلم الإيجنت قبل اكتمال الرد ووصول الطرف الآخر. Mute/unmute والاستلام/التسليم وإنهاء المكالمة فعليًا، مع مزامنة حالة زر التشغيل بين الهاتف والسيرفر. لا تخريب لسلوك Wi-Fi العامل أثناء علاج 4G أو الانتقال بينهما.
- اختبار حقيقي على Xiaomi الحالي مع بيانات الهاتف وWi-Fi، بما يشمل فقد اتصال شبكة وتعافٍ دون تكرار التهيئة أو فقد سياق المكالمة؛ نجاح WebSocket أو وصول النص فقط لا يساوي صوتًا ثنائي الاتجاه.

### 6.4) الشاشة الأولى للمنتج ومسارات التسجيل
- واجهة Android مختصرة للعناصر الضرورية: حالة Google Live **منفصلة** عن اتصال سيرفر OnTrack، SIM/Agent، بدء/إيقاف، الصلاحيات، الإعداد الأول مرة واحدة، نسخة التطبيق، إشعار تحديث مستقل وزر تحديث. السحب للتحديث العادي لا يفحص ويثبت APK كل مرة؛ فتح لوحة الويب في المتصفح الخارجي.
- واجهة SaaS RTL عربية متجاوبة، Light/Dark وSidebar واضح على الهاتف والكمبيوتر. تظهر Agents وScenario وFlow/Studio وKnowledge وAPI وCalls وDevices وSettings دون أدوات المرحلة الثانية غير المطلوبة في القائمة الأساسية. روابط Flow/Studio تعمل، وFull-screen وحفظ/تحميل وتشخيص Invalid node type تُختبر فعليًا.
- التسجيل والدخول واستعادة/تغيير كلمة المرور لكل دور، بما فيها استمارة ريسيلر مخصصة تربط حساب العميل بريسيلره فقط. الدومين أو الساب دومين الخاص بالريسيلر يعرض هويته وشعاره وlogin/register وصفحاته بعد تحقق ملكية الدومين وTLS وعزل tenant؛ لا يكتفى بعرض شكل دون تحقق من صلاحياته.
- خيار «إظهار الريسيلرز» إذا أُغلق يمنع الإظهار في قوائم ورسائل وخطط التسجيل ويمنع الإنشاء غير المصرح من API مباشرة، مع **الحفاظ على الحسابات والاشتراكات والربط الموجود** وعدم حذف أي بيانات.

### 6.5) المعرفة والعمليات الحقيقية والتقارير
- Knowledge Base لكل Tenant/Site/Agent بفولدرات وصلاحيات/إصدارات وملفات PDF/DOCX/TXT/MD/روابط، dedupe والمصادر المتعارضة وindex status ومزامنة مقيدة، مع TTL للمعلومات شبه الثابتة وعدم التعامل مع بيانات حجز/سداد حية من cache قديم.
- Flow Builder ليس رسمة فقط: عقد Intent/Reasoning/Knowledge/Tool/Validation/Approval/Fallback مع Draft/Test/Publish/Rollback وtraces لكل انتقال؛ يجيب استفسارًا جانبيًا ثم يُكمل السيناريو دون فقد البيانات.
- WHMCS: قراءة الخدمات والفواتير، تأكيد الهوية، إنشاء/متابعة تذكرة بعد موافقة العميل والحصول على رقم التذكرة الحقيقي؛ لا تعليق أو حذف/إغلاق خدمات أو تذاكر آليًا. Laravel/REST/الحجز: عرض المتاح → جمع البيانات → قراءة التأكيد → API write بموافقة → رقم العملية الفعلي؛ فشل الـAPI لا يتحول لتأكيد لفظي.
- بيانات تقرير المكالمة: call_id، بداية/نهاية ومدة، رقم/اسم المتصل إن ثبت، حالة النجاح/الرفض/التعذر، transcript متصل قدر الإمكان، summary سياقي، Tool trace منفصل، طلب موظف ومتابعة/ID حقيقي. إظهار الأرقام الأصلية للمخولين في بيئة التجربة دون تسريب أسرار API/كلمات مرور أو إتاحة سجلات tenant آخر. لا إدعاء وجود تسجيل صوت أو handoff خارجي لم ينفذ.

### 6.6) حماية APK والمحرك الصوتي — تعريف القبول الأمني
- **المطلوب ألا يحمل Base APK كود تنفيذ المحرك الحساس إذا أمكن فصله:** مكونات capture/injection/audio routing والمنطق الخاص خارج الحزمة الأساسية في خدمة/وحدة تُحمّل أو تُفعّل فقط بعد المصادقة والترخيص، مع توقيع وتشفير والتحقق من SHA-256 وحقوق الحساب. لا مفاتيح ثابتة أو source/prompts خاصة داخل APK. لا يكفي R8 أو حذف التعليقات وحده.
- الاعتراف بالحد التقني: أي مكون ينفذ محليًا على جهاز العميل قد يُفحص ديناميكيًا؛ لا ضمان مطلق لاستحالة استخراجه. شرط القبول الأمني: فحص وفك Base APK لا يكشف الوحدة المنفصلة، مع اختبارات tamper/signature/offline/license/reverse engineering للمكونات المتبقية. الحفاظ على تراخيص المصدر المفتوح الإلزامية وعدم إتلاف ملفات المستخدم.
- عزل الأجهزة والشرائح والمفاتيح حسب tenant، وقوائم endpoint allowlist ومنع SSRF، والتعامل الآمن مع تشخيص ADB/USB/Wireless debugging دون Root أو Shizuku أو Accessibility أو Gateway/LiveKit كشرط.
- OTA الواجهة وNative بتوقيع معروف وSHA manifest وrollback؛ **لا نشر Native مختلف بنفس versionCode مع SHA مختلف عن إصدار حي**، بل زيادة الإصدار والتحقق من شهادة Android وحفظ pairing. تثبيت Native من خارج Play يخضع لموافقة Android وآليات المنصة؛ لا ادعاء تثبيت صامت غير مثبت.

### 6.7) فلو التنفيذ والتحديث الذي اتُّفق عليه
- عند **صدور أمر تنفيذ منفصل** فقط: Source SHA ثابت → Build عند الحاجة مرة واحدة → Test شامل → Sign/verify → Publish لتعديلات الموقع أولًا إذا عليها اعتماد متبادل، ثم ملف APK والـOTA → Verify خارجي من host receipt + HTTPS + signed manifest/SHA + دخول فعلي → اختبار الهاتف/SIM → Report مختصر بالأدلة والحالة. **كتابة هذا الملف ليست أمرًا ببدء الفلو.**
- **ممنوع تكدس GitHub Actions عمدًا:** لا Pushات إضافية لمجرد المتابعة، ولا إنشاء PRs أو Runs متعددة بلا ضرورة، ولا Workflow جديد بدل إصلاح القائم. تشغيل واحد مطلوب ومحدد، concurrency/queue control، وتحليل logs قبل إعادة تشغيل. لا إنشاء أي جدولة تطوير/فحص ساعية أو تلقائية دون تكليف صريح.
- إذا طُلب إلغاء عمليات، يُستخدم إجراء إلغاء حقيقي ويُراجع queued/pending/in_progress/waiting؛ إيقاف Runner وحده لا يلغي queue. لا تُعلن حالة صفر دون قياس فعلي.
- **فصل الأدلة:** SPEC_APPROVED لا تعني CODED؛ CODED لا تعني CI_PASS؛ بناء وتوقيع APK لا يعني Host Deploy؛ رفع GitHub Release لا يعني OTA مفعّلًا؛ Host receipt لا يعني مكالمة SIM حقيقية ناجحة. لا إعلان v1.0.0 Stable قبل تحقق جميع بنود المرحلة الأولى وCI وhost وauthenticated UI واختبارات الجهاز.
- التقرير النهائي لكل نشر يذكر branch/commit، رقم run، versionCode/versionName، SHA256، شهادة التوقيع، نتائج الاختبارات، رابط الملف المستضاف، manifest العام، إيصال نشر الموقع، ونتائج تجربة SIM؛ الفشل/العائق يُذكر صراحة. لا إغلاق المهمة بعد نجاح build أو upload على GitHub فقط. لا تعطيل للإعدادات أو الحسابات الحية من غير نسخة رجوع واختبار.

### 6.8) البنود المؤجلة إلى Phase 2 — محفوظة لا تُحذف
- مكالمات الحملات الصادرة المجدولة، استيراد جهات الاتصال من الهاتف/CSV/Excel/TXT، إعادة المحاولات، الأصوات الإضافية والاستنساخ، توسيع قنوات WhatsApp/Telegram/social/video، واختبارات ضغط 10–20 مكالمة: تبقى موثقة في نسخ المشروع والخطط القديمة، لكنها **ليست بوابة واجهة المرحلة الأولى المختصرة**.
- عند طلب موظف بشري: في Phase 1 يسجل السبب والتفريغ والملخص والنتيجة دون الإيحاء بأن handoff تم. **طلب الاتصال بالمدير بعد انتهاء المكالمة بـ10 ثوانٍ مع ملخص صوتي** وإدارة جهات الاتصال والتوجيه الفعلي محفوظ لتنفيذ Phase 2.
- في تكامل WhatsApp لاحقًا، تدخل موظف بشري يوقف رد AI **15 دقيقة** حسب سياسة القناة وCoexistence مع WHMCS؛ هذا لا يثبت اكتمال مكالمات SIM.
- نقل أي بند بين المرحلة الأولى والثانية يتطلب موافقة جديدة صريحة، لا اجتهاد منفذ ولا حذف كود قديم دون Backup.

### (4) أحكام ملزمة لمنع تكرار ادعاءات الوصول الخاطئة
