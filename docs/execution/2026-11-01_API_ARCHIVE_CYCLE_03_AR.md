# دورة تنفيذ — 2026-11-01 — حماية API من الوصول إلى الأرشيف

**المشكلة:** `/saas/console/api/v1/` كان يقرأ المواقع المؤرشفة والإيجنتات المؤرشفة ومعرفة الإيجنت، ويقبل إضافة Lead إلى موقع تم أرشفته من الواجهة، رغم أن UI منع إضافة جهة اتصال إليه.

**الإصلاح:** تطبيق حالة `active` على المواقع في قائمة المواقع، التحقق من حالة الموقع المرتبط بمفتاح API، منع عرض الإيجنتات `archived` أو إرجاع المعرفة من موقع غير نشط، ومنع `lead.create` على موقع مؤرشف. لا حذف بيانات أو تغيير مخطط قاعدة البيانات.

**الاختبارات المطلوبة:** `tools/test_voice_api_http.php` يعمل مع `tools/test_voice_saas_console.php` ويشغّل الـAPI الحقيقي عبر خادم PHP محلي وقاعدة SQLite تجريبية؛ يتحقق من GET sites/agents/knowledge، منع تسريب معرفة مؤرشفة، POST lead على موقع مؤرشف (403 ولا إدراج)، رفض tenant آخر، استمرار قبول Lead على موقع نشط، ورفض مفتاح ملغى.

**حالة الإثبات عند إنشاء الملف:** CODED في فرع `fix/api-archived-tenant-resources-20261101` وPR #10؛ نتائج CI والنشر تُسجّل في CHECKPOINT بعد ظهورها. هذا لا يغلق Trash/Restore، ولا يثبت مصادقة المستخدم في المتصفح، ولا يثبت Android أو دفعًا فعليًا.

**مهمة SSO المستقلة:** PR #9 ما زال مفتوحًا عند بدء هذه الدورة؛ لم نعدّل ملفاته ولم ندمجه. المطلوب مراجعة staging أمنية قبل إنتاجه.

**الخطوة التالية:** بعد CI ناجح، دمج PR #10 (إذا لم يظهر تعارض)، متابعة workflow النشر وreceipt على الهوست، ثم تحديث CHECKPOINT والخطة؛ استكمال SSO أو 2FA/Trash وفق ترتيب الخطة.
