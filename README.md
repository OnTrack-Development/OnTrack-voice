# تعليمات إلزامية لتطوير المشاريع باستخدام AI Coding Agents

## 1. اختبر كل نتيجة قبل اعتمادها
- لا تعتمد على أول كود تنتجه باعتباره صحيحًا.
- أنشئ اختبارات آلية (Evals) للوظائف الأساسية.
- اختبر حالات النجاح والفشل والحالات الطرفية.
- أعد تشغيل الاختبارات بعد التعديلات المهمة.
- لا تعلن نجاح أي مهمة دون دليل اختبار فعلي.

## 2. راجع عملك وصحّح أخطاءك تلقائيًا
- بعد كتابة الكود، نفّذ الاختبارات المناسبة.
- افحص الأخطاء والتحذيرات والسجلات.
- أصلح المشكلات المكتشفة تلقائيًا.
- أعد الاختبار بعد الإصلاح.
- كرر دورة الإصلاح والتحقق حتى تنجح الاختبارات أو يظهر عائق حقيقي.
- لا تطلب مني اكتشاف الأخطاء التي تستطيع اكتشافها بنفسك.

## 3. اجعل الكود المصدر الأساسي للمعلومات
- اقرأ الكود الحالي قبل تنفيذ أي تعديل.
- ضع التعليقات التقنية المهمة بجوار الكود المرتبط بها.
- لا تنشئ ملفات توثيق متكررة دون ضرورة.
- احتفظ بالقرارات المعمارية والتعليمات العامة داخل `CLAUDE.md`.
- عند وجود تعارض بين التوثيق والكود، تحقق من السلوك الفعلي وحدّث المعلومات القديمة.

## 4. حسّن صياغة المهام تلقائيًا
- حلّل طلبي وافهم الهدف والنتيجة المطلوبة.
- حوّل الطلب داخليًا إلى مواصفات تنفيذ دقيقة وقابلة للاختبار.
- حدد الملفات والوظائف المتأثرة.
- ضع معايير نجاح واضحة.
- نفّذ مباشرة دون مطالبتي بإعادة صياغة الطلب.
- لا تغيّر الهدف الأصلي أو تضف وظائف غير مطلوبة.

## 5. أدِر نافذة السياق بذكاء
- حمّل فقط الملفات والأدوات اللازمة للمهمة.
- تجنّب قراءة ملفات ضخمة لا علاقة لها بالتعديل.
- لا تفعّل أدوات MCP غير المطلوبة.
- استخدم `/compact` عند الحاجة لتقليل استهلاك السياق.
- احتفظ قبل الضغط بملخص للقرارات والنتائج والأخطاء المفتوحة.
- لا تفقد سياق المشروع أو تعيد تنفيذ أعمال مكتملة.

## 6. اعمل وفق تعريف واضح للاكتمال
- تعامل مع كل مهمة باعتبارك مسؤولًا عن تنفيذها بالكامل.
- اختر التفاصيل التقنية المناسبة دون أسئلة غير ضرورية.
- لا تعتبر كتابة الكود وحدها إنجازًا.
- المهمة تكتمل بعد التنفيذ والمراجعة والاختبار والتحقق من عدم كسر الوظائف السابقة.
- نفّذ البناء والنشر عندما تكون مطلوبة وتتوفر صلاحياتهما.
- لا تستبدل القرارات الصريحة مني بافتراضاتك.

## 7. شخّص المشكلة قبل تعديل الكود
- افحص السلوك الحالي أولًا.
- اقرأ السجلات وتتبع مسار التنفيذ.
- قارن بآخر إصدار مؤكد أنه يعمل عند وجود تراجع.
- حدد السبب الجذري والأجزاء المتأثرة.
- اذكر التشخيص باختصار، ثم نفّذ الإصلاح دون انتظار موافقة إضافية ما دام ضمن نطاق الطلب.
- لا تستخدم حلولًا مؤقتة تخفي العطل بدل إصلاح سببه.

## 8. نفّذ الأعمال المستقلة بالتوازي
- قسّم المهام الكبيرة إلى أجزاء مستقلة.
- شغّل الوكلاء الفرعيين بالتوازي عندما يكون ذلك متاحًا وآمنًا.
- امنع تعديل نفس الملفات بالتزامن دون تنسيق.
- اجمع النتائج في نسخة موحدة.
- شغّل الاختبارات الشاملة بعد الدمج.
- لا تقسّم العمل إلى مراحل انتظار منفصلة إذا كان يمكن إنجازه في عملية تنفيذ واحدة.

## 9. استخدم استراتيجية Fan-out / Fan-in
- استخدم النماذج الأقل تكلفة للبحث والتحليل وجمع المعلومات عندما تكون متاحة.
- وزّع المهام الاستكشافية المستقلة عليها بالتوازي.
- استخدم النموذج الأقوى لمراجعة النتائج واتخاذ القرارات المعقدة.
- تحقّق من النتائج قبل اعتمادها.
- لا تكرر العمل بنموذج مكلف إذا كانت النماذج الأقل تكلفة تستطيع إنجازه بالجودة المطلوبة.

## 10. حدّث CLAUDE.md باستمرار
- راجع `CLAUDE.md` عند بدء العمل.
- حدّثه عند اكتشاف قاعدة تقنية مهمة أو قرار معماري جديد.
- وثّق الأخطاء المتكررة وأسبابها والحلول المؤكدة.
- احذف التعليمات القديمة أو المتعارضة.
- اجعل محتواه مختصرًا وواضحًا وقابلًا للتنفيذ.
- تجنّب القيود السلبية المكررة التي لا تخدم المشروع.

## 11. جهّز خطة بديلة عند تعطل النموذج
- اكتشف أعطال مزود الذكاء الاصطناعي والأخطاء المؤقتة.
- أعد المحاولة بشكل محدود وآمن.
- استخدم نموذجًا بديلًا معتمدًا إذا كان متاحًا.
- احتفظ بحالة المهمة والملفات المعدلة ونتائج الاختبارات.
- استكمل من آخر نقطة صحيحة دون تكرار التعديلات.
- لا تدّعِ استمرار العمل أو إتمامه عند فقدان القدرة على التنفيذ.

## القاعدة النهائية: Definition of Done

لا تعتبر أي مهمة مكتملة إلا بعد:

1. فهم المطلوب ومراجعة الكود المتأثر.
2. تشخيص المشكلة إذا كانت المهمة إصلاحًا.
3. تنفيذ التعديل المطلوب بالكامل.
4. مراجعة الكود والتغييرات.
5. اجتياز الاختبارات ذات الصلة.
6. التحقق من عدم تعطيل الوظائف السابقة.
7. تحديث التوثيق الضروري.
8. إجراء Commit وPush عند طلب العمل على المستودع.
9. تنفيذ Build وDeploy عند طلب النشر.
10. تقديم تقرير نهائي يوضح ما نُفذ، ونتائج الاختبارات، ورقم Commit، وحالة النشر، وأي عوائق متبقية.

**تعليمات أساسية:** نفّذ المطلوب بدل الاكتفاء بشرحه. لا تعلن النجاح قبل التحقق. لا تطلب موافقات متكررة على خطوات داخلة في نطاق المهمة. ولا تنفّذ عمليات حذف أو تغييرات إنتاجية خطرة خارج التفويض الممنوح.

**منهج التنفيذ الإلزامي لكل مشاريع OnTrack:** تشخيص ← تنفيذ ← اختبار ← تصحيح ← بناء ← نشر ← تحقق، حسب نطاق المهمة وصلاحيات المشروع. **عند تعذر أي خطوة، اذكرها عائقًا صريحًا ولا تسمّ المهمة مكتملة.**

**التجربة الحالية (4 نوفمبر 2026):** [فحص ملفات صوت AI على الكمبيوتر عبر GitHub Actions Runner](.github/workflows/voice-local-ai-inventory.yml) — تشغيل يدوي على Windows self-hosted، يجرد الملفات الصوتية وأوزان النماذج فقط، ويرجع النتائج في Artifact. ثم نختبر **Habibi-TTS EGY** وحده (نص ← صوت مصري). **Dograh مستبعد من الاختبار الحالي**؛ ملف [البحث السابق](docs/research/DOGRAH_FIRST_LOCAL_TEST_2026_11_04_AR.md) محفوظ للمرجعية التاريخية فقط. لم يُثبت أي تشغيل على كمبيوتر المالك بعد.

## قواعد مختصرة

- آخر قرارات المالك في `docs/discovery/DECISIONS_AR.md` تعلو على المقترحات القديمة والمراجع المستوردة.
- Phone Link وVoicemeeter مستبعدان. LiveKit ليس اعتمادًا مطلوبًا. لا شراء Gateway لكل عميل كشرط إطلاق.
- المسار الاقتصادي الجاري تقييمه هو Android + الشريحة الموجودة؛ توافقه مع Redmi Note 12 Pro 5G غير مثبت.
- Gemini Live الحالي يعاد استخدامه؛ لا نغيّر محرك AI لمجرد توصيل الهاتف.
- التوكنات والمفاتيح الخاصة وإعدادات الهوست المحلية لا تدخل Git، حتى مع كون المستودع Private.
- ترتيب الوثائق لا ينشر شيئًا على الموقع. لا ترفع `docs/` و`reference/` و`ops/` إلى مجلد الموقع العام.
- لا تساوِ بين نجاح GitHub/Cron أو SIP registration وبين مرور صوت مكالمة حقيقية.
