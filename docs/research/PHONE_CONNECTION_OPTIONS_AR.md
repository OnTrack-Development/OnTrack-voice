# طرق ربط رقم الموبايل — سجل البحث وحدوده

**تحديث حاكم30أكتوبر2026:** Shizuku وشراء الهاردوير وعقود الاتصالات الجديدة مستبعدة. هذا الملف يحتفظ بسجل البدائل؛ المرجع الحالي هو [البحث الموسع](2026-10-30/SOFTWARE_SIM_VOICE_RESEARCH_AR.md). المرشح embedded ADB/shell غير مثبت على الهاتف. لا تتبع وصف «الجاري تقييمه» القديم كأمر تنفيذ.

هذا سجل البدائل التي ناقشناها، لا قائمة خدمات اشتريناها أو توصيات شراء نهائية. يفرق بين مواصفات المورد/تقارير مستخدمين وبين اختبار هاتف المالك. روابط المصادر وسجل مراجعتها في [SOURCES.json](SOURCES.json).

## لماذا الموقع وحده لا يكفي؟

الكود الحالي يبث مدخل المتصفح إلى Gemini. هذا يثبت مسار browser audio في المصدر، ولا يمنح الموقع تلقائيًا وصولًا لصوت مكالمة SIM. نحتاج وسيطًا فعليًا يخرج صوت شبكة المحمول ويعيد رد الإيجنت إليها. Remote shell وCron وQR pairing طبقات تحكم، وليست هذا الوسيط.

## Voice SIP Agent — المرشح الأساسي

المصدر: [sparkcyf/android-voice-sip-agent](https://github.com/sparkcyf/android-voice-sip-agent)، و[TECHNICAL.md](https://github.com/sparkcyf/android-voice-sip-agent/blob/main/TECHNICAL.md).

الفكرة المعروضة من المشروع هي ربط المكالمة الخلوية مع SIP باستعمال Shizuku وصلاحيات/API غير متاحة لتطبيق عادي. التشغيل العادي يحتاج إعداد SIP؛ لا يوجد عندنا PBX مثبت من تلك المناقشة. البرنامج لا يصبح موصولًا بسيرفرنا لمجرد تثبيته.

الدليل التقني يتضمن **Echo incoming calls (test)** لتجربة الهاتف دون PBX، وإعداد Direct telephony مع Mute call audio OFF. نستخدمه كاختبار أولي ونطلب logs وA/B قبل إعلان النجاح. وثيقة المشروع ليست إثبات توافق جهاز المالك.

تقرير مستخدمين في [Issue1](https://github.com/sparkcyf/android-voice-sip-agent/issues/1) وصف أجهزة ومشغلين في كولومبيا: التسجيل وHealth كانا ناجحين رغم مشاكل صوت، ثم وردت نتائج أفضل بإعدادات معينة. هذا **تقرير طرف آخر** وليس اختبارًا لنا أو لمصر أو Note12Pro5G. تفاصيل دقيقة تتغير بتعليقات issue؛ لا نعتمد سعة أو استقرارًا تجاريًا منه.

عند بناء fork تجاري، اقرأ LICENSE الفعلي وإصداره والتزامات توزيع التطبيق قبل الدمج. ظهرت أوصاف ترخيص متباينة في مراجع سابقة؛ لم نغلق مراجعة الترخيص أو نوزع fork هنا.

## ما يمكن أن يفعله تطبيقنا المخصص

تسجيل دخول أوQR يمكنه تحميل server endpoint وربط tenant/رقم وتوليد channel credentials وتقديم فحص صحة وصلاحيات بخطوات أقل. لا ينشئ API صوت غير متاح على الجهاز، ولا يلغي قيود reboot لخدمة Shizuku بلاroot. يبنى onboarding بعد نجاح الصوت، لا قبله.

## حدود الاستضافة

PHP/Python في الحساب يكفيان لقناة إدارة ملفات وأوامر مثبتة. لا نملك بعد دليل persistent audio process أو منافذ SIP/RTP العامة أو جسر الهاتف. يجب فحصها قبل اختيار مكان PBX/bridge؛ تشغيل صوت لحظي عبر Cron كل دقيقة ليس حلًا.

لا يوجد «أفضل حل نهائي» مثبت حتى الآن: المنتج محدد، والمرشح الاقتصادي Android يحتاج الاختبار على الجهاز. معيار القرار القادم هو الصوت الحقيقي والتعافي والتكلفة الفعلية، لا سهولة شاشة pairing فقط.
